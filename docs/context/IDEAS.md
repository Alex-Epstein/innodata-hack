## 2. Visual: rigor and analysis bank

**Proving each item is valid**
- Answer comes from the parameters (by construction)
- **Pixel oracle**: separate CV code recovers the answer from the PNG alone (answerable from the image)
- DOM oracle for UI screenshots (exact boxes and values)
- Ambiguity guard: label overlap, minimum size and contrast, near-tie rejection, a tolerance band per item
- **Blind baseline**: the question with no image (text leakage, guessing from priors)
- Human agreement on a sample; judges add labels live at the demo
- Validity funnel with the rejection rate at each stage

**Finding out why models fail**
- **Counterfactual twins**: change one value; does the model's answer change?
- **Perception vs reasoning split**: extract the data first, then answer; score each step
- **Crop test**: crop to the relevant region; if accuracy recovers, it's a localization failure
- **Resolution sweep**: is the failure caused by downsampling in the model's vision encoder?
- **Invariance tests**: same scene with a different font, palette or layout; the answer must not move
- **Paraphrase consistency**: ask 3 ways and measure agreement
- **Calibration**: ask for confidence and plot a reliability diagram. Overconfident on the hardest items?
- **Image prompt injection**: text inside the image says "the answer is 7". Does the model obey? (a red-teaming
  angle, and Innodata does trust and safety work)
- Chain-of-thought vs direct answer, per capability
- Computed failure taxonomy: off by one tick, neighbor bar or cell, wrong series, unit slip, hallucinated value

**Statistics**
- Bootstrap 95% CIs; logistic psychometric fit; **breaking point** per model per knob, with its own CI
- IRT (difficulty and discrimination per item, ability per model); drop items that don't tell models apart
- Adaptive staircase search: find a breaking point in about 20 calls instead of 500
- Paired tests between models on the same items (McNemar)

## 4. Coding: rigor bank
- Tests pass on the reference, fail on the base repo and on a stub
- **Mutation score**: AST mutators (flip comparisons, off-by-one, drop a branch, swap arguments)
- **Impostor solutions**: a red model writes plausible but wrong patches; the tests must reject them
- **Cheater agent**: told to pass by any means (hardcode, edit tests, monkeypatch, sys.exit(0)); a hackability score per task
- Hardcode detection: rerun hidden tests with perturbed inputs
- Test-file tamper detection (hash the tests before and after)
- Diff coverage: the tests actually execute the lines the patch changed
- Flake check: 3 runs in shuffled order
- Property-based tests (Hypothesis) as a second oracle
- **Spec ambiguity via differential testing**: 3 models solve from the spec alone; where their outputs disagree, flag the sentence responsible
- Leakage check (the spec doesn't contain the code); AST dedupe
- Difficulty from data: solve rate across models, then IRT
- Realism score: how well the tickets match the style of real GitHub issues (structure, length, acceptance criteria)
- Sandbox: subprocess, timeout, no network
- Cost and time per kept task

## 5. Framings that make Innodata judges lean in
- **"RL-ready environments"**: every item has a reward you can verify and can't game. Labs buy exactly this.
- **"Find the weakness, then make the training data"**: the factory produces items right at each model's
  breaking point. Cheap proof: do 3 in-context examples from that failure category raise accuracy? Before/after number.
- **Contamination-proof**: fresh items every run, plus a canary string in the dataset card.
- **Data business metrics**: cost per kept item, items per minute, rejection rate. A data company thinks in these.
- **Auto-generated dataset card** (what's in it, how it was validated, known limitations).
- **Plugin architecture**: a new capability is one file with `generate()`, `oracle()`, `knobs`. Show adding one live.

## 6. Demo and engagement bank
- **Judges take the eye exam** (timed); their score goes up next to the models. Serve it on a QR code if hosting is free
- **Predict the breaking point**: judges guess where a model fails, then we reveal the curve
- **Turn the knob**: a slider generates a fresh item, a live model call, truth vs answer
- **Sneak a bug past the tests** (Coding): a judge plants a bug and the kill board updates
- **Out-cheat the tests** (Coding): a judge tries to pass a task without solving it
- **Watch the funnel**: items flow through each check live, with rejections shown and the reason for each
- Printed failure gallery as a one-page handout
- Image-injection moment: a chart with tiny text saying "answer 42", and the model says 42

## 8. How to pick the track in 5 minutes with the team
1. Ask the organizers which models are available and how much quota there is (vision calls cost more tokens).
2. Ask who on the team is strongest at what: CV/graphics leans Visual, backend/testing leans Coding.
3. Look around the room: if most teams go Visual, Coding has fewer competitors (and vice versa).
4. Default if it's a tie: **Visual #1 or #2** (fewer moving parts, faster demo reaction, your CV strength).
