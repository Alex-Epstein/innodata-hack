1 Challenge description
How can we automatically produce realistic visual reasoning tasks, with answers that can be verified, that frontier multimodal models struggle with?
Your team will build an automated pipeline, a small task factory, that generates images, questions about them, and reference answers computed by code. You choose the domain, the image type, and how the pipeline works.
Choose images people actually rely on: diagrams, plots, maps, plans, schematics, charts, documents, and other visuals found in real tools, publications, and teaching material. Realistic tasks make the results speak to how useful a multimodal assistant is in practice, not to toy puzzles. A wrong reading of a real image feeds straight into real decisions or learning, and a confident wrong answer is worse than no answer.
Every image must be verifiable and generated by code, not by an AI image model, so its content is known exactly. It must also have real-world value, for example in a business application or in training and education.
Render every image from structured data, then compute the reference answer from that same data by code. The answer is then independent of any model, and separate checks confirm the image actually supports it.
The tasks should be ones frontier models struggle with. If strong models answer a set reliably, it tells us little about where they fail. The difficulty should come from what the task asks of the model, not from an unfair image or an ambiguous question.
Use the generated tasks to evaluate two frontier multimodal models: run them against the tasks, record their responses, and analyse what made them fail. Demonstrate that the pipeline can build, check, and score a fresh task end to end.
The expected outcome is a reusable generation-and-evaluation pipeline, sample tasks, verification evidence, and clear findings. Aim for a focused, reliable prototype, and explain its limitations honestly.

4 Quality requirements
A task counts only if its answer can be verified from data and its image looks like a real image of its kind. Tasks that fail either test are excluded, never scored as model failures.
Ground truth
Data first, image second. Create the structured data before rendering; the image is a pure function of it. No freehand drawings, screenshots, or AI-generated images, because their contents cannot be verified.
Store it with every task. Save the data as JSON next to the image, with the seed and generator version, so anyone can re-render and audit it.
Answers come from the data. Compute the reference answer by code, never by a person or model reading the image.
The image must match the data. Check that what is visible matches the data (OCR of labels, pixel measurement, re-parsing structure where possible). A mismatch invalidates the task.
Numeric answers need a fair tolerance. When an answer is read off a continuous scale, state the tolerance in the prompt and base it on how precisely a careful reader can read that image: tight enough that common wrong methods fall outside it, loose enough that a careful human reading meets it. A tolerance no careful reader could meet makes the task invalid.
No ground truth, no task. An image without verifiable data points is excluded.
Hidden from the model. The evaluated model sees only the image, the question, and the response instructions.
Realism
Mimic real sources. Match the look of the software, publications, or materials your image type actually comes from, so the image could pass for a real one.
Realistic content. Plausible titles, labels, units, values, and names for the domain, including physically plausible parameters where relevant. No "Series 1" or "Node A" unless the real source would show it.
Realistic imperfections. The density, annotations, similar colors, small fonts, and clutter that real images of this kind carry, but never unreadable. Difficulty belongs in the reasoning, not in illegibility.
Vary styles within the convention. Use a few distinct styles (theme, palette, layout, density), not just recoloring.
Cite your references. For each image, name one or two real examples you based it on, such as a published figure, a software screenshot or a public report.
Difficulty
Tasks should be difficult for frontier models. How you get there is up to your team: pilot early, see what the models handle easily, and make the next version harder.
Hard, but fair. Every answer is still unique, computed by code, and visible in the image, and the question needs the image to answer. A task that is hard because it is unreadable or ambiguous is invalid, not difficult.
Domain knowledge must be standard. When a task relies on domain knowledge, the method it requires should be textbook-level for the field; state any constants or conventions that are not. Difficulty should come from reading the image and applying the method, not from obscure facts.
Evaluation
Fair settings. Use temperature=0, reasoning effort = high, and a fixed max_tokens high enough for long reasoning
Complete responses only. All model responses in the reported evaluation must be complete, with no truncation or API error: each model returns a complete reply (finish_reason = stop) to every accepted task. Retry transient API errors (429, 5xx, timeouts) with backoff. If a call keeps failing or a reply is cut off by the token limit, find the cause, fix it (for example, raise max_tokens), and run the evaluation again; when you change a setting, re-run every task, not only the affected ones.
Results must be transparent. Log every raw response and report all results from the reported evaluation. Do not select only the best response from repeated attempts.

Repository layout and file formats
Submissions are checked with common tools that read the layout and files below. Work in a different layout is still judged, but some checks cannot be run on it.
Validation code in validate/. All code that checks your tasks (validity checks, the independent re-computation of reference answers, legibility checks), in a folder named validate at the root of the repository.
Evaluation code in eval/. All code from task to reported number (model calls, the prompt, answer extraction, scoring, and the report), in a folder named eval at the root of the repository.
Run the code you submit. The pipeline must run the code in these two folders, not a copy kept elsewhere. Code in other folders, such as your generator, may be imported.
Runs in Docker. The pipeline must run in Docker. A Dockerfile at the root of the repository builds an image that holds the whole pipeline and its dependencies, so only Docker is needed to run it. Judges build the image and run the commands in the README's Run in Docker section exactly as written. Pass the OpenRouter key at run time as the OPENROUTER_API_KEY environment variable; never copy a key or a .env file into the image.
README at the root. One README.md at the root of the repository, with these three sections under these headings:
Reported folders: the path, from the repository root, of the task folder and of the results folder of the final tasks to be evaluated for this challenge.
Pilot results: the pilot scores, and the changes you made to the generator because of them.
Run in Docker: the Docker commands that build the image and (1) rebuild the 10 reported tasks from their seeds, identical to the submitted ones (same images, questions, and reference answers), then evaluate both models on them and score the answers.
Task file. One tasks.jsonl in each task folder, with one JSON object per line and the fields below. Other fields, such as the seed, generator version, and check results, are welcome.
Field
Content
task_id
Unique ID, also used in the results.
image
Image path, relative to the task folder.
question
The question exactly as sent to the model.
answer
The reference answer: a number, a label, an option letter, or a list for a sequence.
answer_type
number, integer, label, multiple_choice, or sequence.
tolerance_rel or tolerance_abs
For non-integer numbers: the accepted relative error (0.05 means ±5%) or the absolute error in the answer's unit. Use one, and state the same tolerance in the prompt.
options
For multiple_choice: the options, in letter order.

Results file. One responses.csv (or responses.jsonl) in results folder, with one row per model and task and the columns below.
Column
Content

The exact model ID used.
task_id
As in tasks.jsonl.

ok for every row: the model returned a complete reply.

The answer your code extracted from the reply; empty if none was found.

The kind of question, as set by your generator (for example the question template or variant), so results can be broken down by the reasoning required.

The model's full reply, as returned.

6 Rules and judging
Rules
Participation: teams of 5 participants; all members participate in person.
Build time: 4 hours 30 minutes for the core solution. Presentations and judging are outside the build window. Submit the state of your work by the deadline.
Allowed tools: AI coding assistants, model APIs, open-source libraries, and general-purpose utilities, subject to the access and budget rules. Disclose pre-existing code and reused components.
Teamwork: work within your team. Organizer guidance is allowed, but people outside the team must not build your submission.
Access and budget: use the organizer-provided keys within the allocated budgets. Personal paid accounts and additional API spending are not allowed.
Transparency: clearly identify manual interventions, incomplete functionality, and limitations. Demonstrations and reported results must reflect the submitted work.
Partial completion: incomplete submissions are accepted and receive credit for the work demonstrated, under the same rubric.
Judging
Judges score each criterion from 0 to 5, for a maximum of 35 points.
Criterion
What judges assess
Realistic, useful visuals
Images and questions that look like real material of their kind and have real-world value, for example in business, training, or education.
Reliable generation pipeline
A functioning pipeline that generates fresh, valid tasks from structured data.
Fair, verifiable tasks
Questions that require the image and have a unique answer, computed from the data and supported by what is visible.
Task difficulty
Tasks are genuinely hard for strong multimodal models, shown by the evaluation.
Meaningful variation
Substantive differences across tasks in the reasoning required — not rewording or recoloring.
Model evaluation
Actual model runs, consistent scoring, and findings supported by the results.
Runnable submission
Code and instructions that let the work be inspected and reproduced. Judges build the Docker image, rebuild the 10 reported tasks and score them, following the README.

Use the following scale: 0 - not demonstrated; 1 - very limited; 2 - partially demonstrated; 3 - meets expectations; 4 - strong; 5 - excellent.
Quality and repeatability carry more weight than task quantity. Task difficulty is assessed, but exact thresholds and weights are not published — build to the qualities above, not to a number. Invalid tasks must not be counted as model failures.
If teams have the same total score, prioritize task validity and reference-answer verification, followed by the ability to generate fresh valid examples.
